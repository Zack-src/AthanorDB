## Phase 13 — Security hardening

Audited 2026-07-30. The auth/teams/invitations system (`apps/server/src/auth/*`, `apps/server/src/routes/{auth,invitations,teams,users}.ts`, `apps/server/src/permissions.ts`) has never had a security pass — items below are new findings, not regressions.

- [x] No rate limiting / brute-force protection anywhere — done 2026-07-31: `@fastify/rate-limit` registered with `global: false` (loose 300/min ceiling) plus per-route limits of **10/minute per IP** on `POST /api/auth/login` and `POST /api/invitations/:token/accept`. Verified live: 12 rapid login attempts returned 10x401 then 429.
- [x] scrypt cost factor below current guidance — bumped 2026-07-31 from N=16384 to **N=65536** (r=8, p=1), with `maxmem` raised since Node's 32MB default rejects it. Measured on the dev machine: 16384=26ms/16MB, 32768=49ms/32MB, 65536=103ms/64MB, 131072=208ms/128MB. Deliberately one step below OWASP's N=2^17, documented in `password.ts`: 128MB *per concurrent hash* is a memory-exhaustion lever on the 1-2GB boxes this gets self-hosted on, and the gap is covered on the other side by the new rate limit + password length cap.
- [x] No max password length — done 2026-07-31: `MAX_PASSWORD_LENGTH = 128`, enforced through a single `checkPassword()` helper shared by invite-accept, both password-change routes and `bootstrap-admin`. Login rejects over-length input *before* hashing (verified: a 5000-char password returns 401 immediately) and `verifyPassword` refuses it as a second layer.
- [x] No cleanup of expired sessions — done 2026-07-31: `purgeExpiredSessions()` in `auth/session.ts`, run at boot and hourly from an `unref`'d interval. Verified: expired row deleted, live row untouched.
- [x] Secure cookie flag is opt-in with no production safeguard — done 2026-07-31: env reading moved into `config.ts`, which warns loudly at boot when `NODE_ENV=production` and `ATHANORDB_COOKIE_SECURE` is unset, and hard-fails on any value other than `true`/`false`. Documented in the README config table.
- [x] No CSRF defense beyond `SameSite=Lax` — done 2026-07-31: an `onRequest` hook rejects any non-GET/HEAD/OPTIONS request whose `Origin` doesn't match the request `Host` (or `ATHANORDB_ALLOWED_ORIGINS`). A missing `Origin` still passes, so curl/scripts/backup tooling keep working. Verified live: cross-origin POST 403, same-origin POST normal, cross-origin GET 200. **Correction 2026-08-09**: the "Vite dev proxy preserves `Host`" assumption above was wrong and had never actually been exercised through `npm run dev` — node-http-proxy rewrites the forwarded `Host` to the proxy *target* regardless of `changeOrigin`, so every state-changing request in dev (login included) arrived as `Origin: localhost:5173` / `Host: localhost:3001` and got a 403. This evidently passed review because it was verified against the production single-origin build (one process serving the built web app, no proxy, Origin trivially equals Host), never against split dev origins. Fixed in `apps/web/vite.config.ts`: the `/api` proxy now forces the original inbound `Host` back onto the proxied request.
- [x] Invitation accept has a TOCTOU race — fixed 2026-07-31: the accept claims the token inside a `db.transaction` with a conditional `UPDATE ... WHERE accepted_at IS NULL`, re-checks the email, and only then inserts. The loser of a race gets a clean 409 instead of an unhandled UNIQUE-constraint 500.
- [~] Invitation delivery is fully manual, no email integration — `routes/invitations.ts` still just returns `inviteUrl` as JSON for an admin to relay by hand. The documentation half of this is done (2026-07-31): the README's "Accounts, teams and invitations" section states outright that there is no email delivery and that the link is a live account-creation credential to be sent over a trusted channel. Real SMTP/nodemailer delivery remains optional/unbuilt.
- [x] No entity-count limits in a project — done 2026-08-09: `packages/shared/src/limits.ts` gained per-parent array-length caps (`MAX_FIELDS_PER_TABLE`=200, `MAX_INDEXES_PER_TABLE`=100, `MAX_COMMENTS_PER_TABLE`=500, `MAX_VALUES_PER_ENUM`=500, `MAX_TABLES_PER_TABLE_GROUP`=500 — clamped the same way string lengths already were, silently truncated) plus `COLLECTION_COUNT_LIMITS`, a top-level per-project cap on each collection (tables 2000, refs 4000, enums/zones 1000, sticky notes 2000, table groups 500 — generous relative to the "revisit at 500+ tables" open decision below; an abuse backstop, not a UX limit). `Room.enforceLimits()` now also deletes back down to the cap after a transaction pushes a collection over it, taking only from *that transaction's own* newly-touched entities so a pre-existing large project is never touched by an unrelated later edit — once a collection is at its cap, further single additions get silently reverted rather than accepted. Also closed a gap found in the process: `TableGroup` (new in this session) wasn't registered in either `clampCollectionValue`'s dispatch or `Room`'s watched collection keys, so its `name` had zero server-side length enforcement — fixed alongside. Unit-tested in `limits.test.ts`.
- [x] Weak email validation — done 2026-07-31: `auth/email.ts` (`isValidEmail`/`normalizeEmail`, 254-char cap, documented RFC-subset regex) used by login, invitation creation and `bootstrap-admin`. Verified: `a@b@c` is now rejected.
- [x] Remove unused `monaco-editor`/`@monaco-editor/react` dependencies — done 2026-07-31: both deps uninstalled (5 packages removed) and the stale `.monaco-editor` selectors dropped from `useEditorKeyboardShortcuts.ts`/`useEdgeRouting.ts`. `dompurify` turned out to also come in via `jspdf`, so `npm audit fix` (non-breaking) bumped it too. Remaining audit finding is `esbuild <=0.24.2` via `vite <=6.4.2` — dev-server-only, and fixing it means a Vite 8 major upgrade, tracked separately if we take it.

## Phase 15 — Reliability & operations

Audited 2026-07-30. Gaps that matter for running this unattended as a real self-hosted service, beyond the already-tracked Dockerfile build bug (Phase 10).

- [x] No graceful shutdown — done 2026-07-31: SIGTERM/SIGINT handlers stop the session sweep, run `flushAllRooms()` (new `Room.flush()` cancels the debounce and snapshots immediately), `closeAllRooms()`, `app.close()`, `db.close()`, with a 10s forced-exit ceiling. Flush path verified directly: an edit made <2s before flush lands in the snapshot and survives a reload. Signal *delivery* could not be exercised here (Windows dev box — Node doesn't receive real SIGTERM), so one live `docker stop` check on Linux is still owed.
- [x] No global process-level error guard — done 2026-07-31: `uncaughtException` logs, flushes every room's state to SQLite and **keeps the process alive** (documented tradeoff: for a collaborative server, dropping every other project's session is strictly worse than continuing degraded, and the known failure paths are already isolated per-connection); `unhandledRejection` logs.
- [x] No real migration system — done 2026-08-09: new `apps/server/src/migrations.ts` — an ordered `MIGRATIONS` array (`{ version, name, up(db) }`), applied by `runMigrations()` in versions-above-current order, each in its own transaction, tracked via SQLite's built-in `PRAGMA user_version` (one integer, no separate migrations table — a deliberate simpler choice than the "versioned-migrations table" phrasing here, since a linear list has no need for per-row bookkeeping). `db.ts`'s two ad-hoc `PRAGMA table_info` + guarded `ALTER TABLE` checks became migrations 1 and 2; a future schema change is a new array entry instead of another one-off check that's easy to forget. Each `up()` still guards its own `ALTER` (belt and suspenders against a database that reached the shape some other way, e.g. an old backup restore) rather than trusting `user_version` alone. 5 new tests in `migrations.test.ts` (fresh DB gets every column + latest version; re-running is a no-op; a DB with the columns already present but a stale version doesn't get double-`ALTER`ed; a brand-new install whose `CREATE TABLE` already has every column still ends up at the latest version). Live-verified against the dev database: `PRAGMA user_version` went from unset (0) to 2, `PRAGMA table_info(projects)` confirmed both columns, and login/dashboard kept working after the restart.
- [x] Backup is one-way — done 2026-08-09: new `apps/server/src/restore.ts` (`npm run restore -- <backupDir> [--owner email]`), the direct counterpart to `backup.ts` — bulk-imports a directory of `.dbml` files, each becoming a **new** project (never overwrites an existing one, so restoring the same backup twice makes duplicates rather than risking data loss). Reuses `applyVisualMetadata`/`toProject` from the engine to restore position/zones/sticky notes from backup.ts's sidecar comment when present, writes straight into a fresh `Y.Doc` via `writeProjectToDoc` and `saveSnapshot` — no server process or live Room needed, same standalone-script style `backup.ts` already uses. `--owner <email>` sets the restored project's owner (there's no "reassign owner" route yet, so this is the only way to make one manageable by someone other than a global admin); without it the projects are still viewable by any user (the standard ownerless/no-team default) but only a global admin can manage them, and the script warns about this loudly. 4 new tests for the two pure helpers (filename→name recovery, arg parsing). Live-verified end-to-end against the dev database: backed up a real project, restored it under a new id with `--owner`, confirmed via the running server's own API that the restored project's DBML export and table/field/enum content matched the original exactly, then deleted the test artifact.
- [x] No request/frame size limits tuned for this app — done 2026-07-31: `bodyLimit` 4MB (up from Fastify's 1MB default, for large DBML/SQL imports) and WebSocket `maxPayload` 8MB, both overridable via `ATHANORDB_MAX_BODY_MB` / `ATHANORDB_MAX_WS_FRAME_MB`.
- [x] No startup config validation — done 2026-07-31: `apps/server/src/config.ts` is the only place reading `process.env` now, validating every value and exiting with a `[config] ...` message on anything malformed. Verified: `PORT=abc`, `PORT=99999` and `ATHANORDB_COOKIE_SECURE=maybe` each exit 1 with a clear message; an uncreatable `ATHANORDB_DB_PATH` fails the same way in `db.ts`.
- [x] Docker container runs as root — fixed 2026-07-31 alongside the Phase 10 build fix: `USER node`, with `/app` and `/data` chowned first.

- [x] Plugin settings / persisted state — done 2026-08-08: `athanor.plugin({ settings: [...] })` declares `string`/`number`/`boolean`/`select` entries (validated in the sandbox bootstrap), values live under `athandordb_plugin_settings` in `localStorage`, the manager renders the form (the plugin supplies data, never markup), and `registry.settingsFor()` merges declared defaults with saved values into every call's context. The second-argument shape was chosen so plugins written against `run(project)` keep working. Selection is read from a ref at call time (a dependency would re-render the toolbar on every click). Both the built-in `reset-link-routing` and the example's snake_case command now scope to the selection when there is one.
- [x] No plugin-defined keyboard shortcuts — done 2026-08-08: `shortcut` on any contribution, parsed by `plugins/shortcuts.ts` (`normalizeShortcut`/`shortcutFromEvent`/`matchShortcut`, modifier required). First plugin to claim a combination keeps it (`registry.shortcuts()`), and typing targets (`input`/`textarea`/`select`/`.cm-editor`/`contenteditable`) are skipped for the global binding.
- [x] Can't get a plugin's source back out — done 2026-08-08: per-plugin download button in the manager writes `<plugin id>.js`.
- [ ] No plugin-provided UI — the Figma model (plugin renders its own HTML in a sandboxed iframe panel, talking over `postMessage`). Much larger than the current Worker model and needs its own security pass; only worth it once a real plugin needs more than a settings form.

- [ ] Plugins are untested — `apps/web` still has no test setup at all (Phase 16), so the registry, the sandbox host's timeout/restart path and the built-in contributions have no automated coverage; the Playwright runs used during development were one-off scripts, not a suite in the repo.

## Open decisions (revisit as needed)

- Auth model: resolved — full email/password auth with sessions, per-project/team permissions, invitations, and an admin console are implemented (`apps/server/src/auth/*`, `apps/server/src/routes/{auth,invitations,teams,users}.ts`, `apps/web/src/{Login,AdminConsole,AcceptInvite,ChangePasswordModal,ProjectTeamsModal}.tsx`) — supersedes the earlier "simple username" plan. No external IdP integration.
- Canvas library: React Flow chosen over building custom SVG/canvas engine, for speed; revisit if performance issues with very large schemas (500+ tables).
- History storage: Yjs update log + periodic SQLite snapshots, avoids storing full doc on every change.
- SQLite as a _SQL import/export dialect_ is not supported by `@dbml/core` (only postgres/mysql/mssql/snowflake/schemarb). SQLite is still used as AthanorDB's own storage engine (unrelated concern). Partly answered by Phase 17: SQLite **export** now ships as the example plugin (generated straight from the `Project`, no parser needed); SQLite **import** would still need a DDL parser.
- Plugin trust model: sandboxed Worker + per-browser install, no server-side plugin store. Revisit if plugins need to be shared across a team — that would mean the server storing third-party code and every user of an instance inheriting an admin's decision to install it.
