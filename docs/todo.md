## Phase 13 — Security hardening

Audited 2026-07-30. The auth/teams/invitations system (`apps/server/src/auth/*`, `apps/server/src/routes/{auth,invitations,teams,users}.ts`, `apps/server/src/permissions.ts`) has never had a security pass — items below are new findings, not regressions.

- [x] No rate limiting / brute-force protection anywhere — done 2026-07-31: `@fastify/rate-limit` registered with `global: false` (loose 300/min ceiling) plus per-route limits of **10/minute per IP** on `POST /api/auth/login` and `POST /api/invitations/:token/accept`. Verified live: 12 rapid login attempts returned 10x401 then 429.
- [x] scrypt cost factor below current guidance — bumped 2026-07-31 from N=16384 to **N=65536** (r=8, p=1), with `maxmem` raised since Node's 32MB default rejects it. Measured on the dev machine: 16384=26ms/16MB, 32768=49ms/32MB, 65536=103ms/64MB, 131072=208ms/128MB. Deliberately one step below OWASP's N=2^17, documented in `password.ts`: 128MB _per concurrent hash_ is a memory-exhaustion lever on the 1-2GB boxes this gets self-hosted on, and the gap is covered on the other side by the new rate limit + password length cap.
- [x] No max password length — done 2026-07-31: `MAX_PASSWORD_LENGTH = 128`, enforced through a single `checkPassword()` helper shared by invite-accept, both password-change routes and `bootstrap-admin`. Login rejects over-length input _before_ hashing (verified: a 5000-char password returns 401 immediately) and `verifyPassword` refuses it as a second layer.
- [x] No cleanup of expired sessions — done 2026-07-31: `purgeExpiredSessions()` in `auth/session.ts`, run at boot and hourly from an `unref`'d interval. Verified: expired row deleted, live row untouched.
- [x] Secure cookie flag is opt-in with no production safeguard — done 2026-07-31: env reading moved into `config.ts`, which warns loudly at boot when `NODE_ENV=production` and `ATHANORDB_COOKIE_SECURE` is unset, and hard-fails on any value other than `true`/`false`. Documented in the README config table.
- [x] No CSRF defense beyond `SameSite=Lax` — done 2026-07-31: an `onRequest` hook rejects any non-GET/HEAD/OPTIONS request whose `Origin` doesn't match the request `Host` (or `ATHANORDB_ALLOWED_ORIGINS`). A missing `Origin` still passes, so curl/scripts/backup tooling keep working. Verified live: cross-origin POST 403, same-origin POST normal, cross-origin GET 200. **Correction 2026-08-09**: the "Vite dev proxy preserves `Host`" assumption above was wrong and had never actually been exercised through `npm run dev` — node-http-proxy rewrites the forwarded `Host` to the proxy _target_ regardless of `changeOrigin`, so every state-changing request in dev (login included) arrived as `Origin: localhost:5173` / `Host: localhost:3001` and got a 403. This evidently passed review because it was verified against the production single-origin build (one process serving the built web app, no proxy, Origin trivially equals Host), never against split dev origins. Fixed in `apps/web/vite.config.ts`: the `/api` proxy now forces the original inbound `Host` back onto the proxied request.
- [x] Invitation accept has a TOCTOU race — fixed 2026-07-31: the accept claims the token inside a `db.transaction` with a conditional `UPDATE ... WHERE accepted_at IS NULL`, re-checks the email, and only then inserts. The loser of a race gets a clean 409 instead of an unhandled UNIQUE-constraint 500.
- [~] Invitation delivery is fully manual, no email integration — `routes/invitations.ts` still just returns `inviteUrl` as JSON for an admin to relay by hand. The documentation half of this is done (2026-07-31): the README's "Accounts, teams and invitations" section states outright that there is no email delivery and that the link is a live account-creation credential to be sent over a trusted channel. Real SMTP/nodemailer delivery remains optional/unbuilt. **Considered 2026-08-09, deliberately not attempted**: this environment has no real SMTP server to send through and verify against, and shipping untested mail-sending code — the exact thing this session's own standard has been "verified live" or clearly labeled otherwise — isn't a trade worth making for an explicitly optional feature that's already fully functional (and documented) via the manual link-relay path. A future pass with a real (or Ethereal-style test) SMTP target to verify against would de-risk this properly.
- [x] No entity-count limits in a project — done 2026-08-09: `packages/shared/src/limits.ts` gained per-parent array-length caps (`MAX_FIELDS_PER_TABLE`=200, `MAX_INDEXES_PER_TABLE`=100, `MAX_COMMENTS_PER_TABLE`=500, `MAX_VALUES_PER_ENUM`=500, `MAX_TABLES_PER_TABLE_GROUP`=500 — clamped the same way string lengths already were, silently truncated) plus `COLLECTION_COUNT_LIMITS`, a top-level per-project cap on each collection (tables 2000, refs 4000, enums/zones 1000, sticky notes 2000, table groups 500 — generous relative to the "revisit at 500+ tables" open decision below; an abuse backstop, not a UX limit). `Room.enforceLimits()` now also deletes back down to the cap after a transaction pushes a collection over it, taking only from _that transaction's own_ newly-touched entities so a pre-existing large project is never touched by an unrelated later edit — once a collection is at its cap, further single additions get silently reverted rather than accepted. Also closed a gap found in the process: `TableGroup` (new in this session) wasn't registered in either `clampCollectionValue`'s dispatch or `Room`'s watched collection keys, so its `name` had zero server-side length enforcement — fixed alongside. Unit-tested in `limits.test.ts`.
- [x] Weak email validation — done 2026-07-31: `auth/email.ts` (`isValidEmail`/`normalizeEmail`, 254-char cap, documented RFC-subset regex) used by login, invitation creation and `bootstrap-admin`. Verified: `a@b@c` is now rejected.
- [x] Remove unused `monaco-editor`/`@monaco-editor/react` dependencies — done 2026-07-31: both deps uninstalled (5 packages removed) and the stale `.monaco-editor` selectors dropped from `useEditorKeyboardShortcuts.ts`/`useEdgeRouting.ts`. `dompurify` turned out to also come in via `jspdf`, so `npm audit fix` (non-breaking) bumped it too. Remaining audit finding is `esbuild <=0.24.2` via `vite <=6.4.2` — dev-server-only, and fixing it means a Vite 8 major upgrade, tracked separately if we take it.

## Phase 15 — Reliability & operations

Audited 2026-07-30. Gaps that matter for running this unattended as a real self-hosted service, beyond the already-tracked Dockerfile build bug (Phase 10).

- [x] No graceful shutdown — done 2026-07-31: SIGTERM/SIGINT handlers stop the session sweep, run `flushAllRooms()` (new `Room.flush()` cancels the debounce and snapshots immediately), `closeAllRooms()`, `app.close()`, `db.close()`, with a 10s forced-exit ceiling. Flush path verified directly: an edit made <2s before flush lands in the snapshot and survives a reload. Signal _delivery_ could not be exercised here (Windows dev box — Node doesn't receive real SIGTERM), so one live `docker stop` check on Linux is still owed.
- [x] No global process-level error guard — done 2026-07-31: `uncaughtException` logs, flushes every room's state to SQLite and **keeps the process alive** (documented tradeoff: for a collaborative server, dropping every other project's session is strictly worse than continuing degraded, and the known failure paths are already isolated per-connection); `unhandledRejection` logs.
- [x] No real migration system — done 2026-08-09: new `apps/server/src/migrations.ts` — an ordered `MIGRATIONS` array (`{ version, name, up(db) }`), applied by `runMigrations()` in versions-above-current order, each in its own transaction, tracked via SQLite's built-in `PRAGMA user_version` (one integer, no separate migrations table — a deliberate simpler choice than the "versioned-migrations table" phrasing here, since a linear list has no need for per-row bookkeeping). `db.ts`'s two ad-hoc `PRAGMA table_info` + guarded `ALTER TABLE` checks became migrations 1 and 2; a future schema change is a new array entry instead of another one-off check that's easy to forget. Each `up()` still guards its own `ALTER` (belt and suspenders against a database that reached the shape some other way, e.g. an old backup restore) rather than trusting `user_version` alone. 5 new tests in `migrations.test.ts` (fresh DB gets every column + latest version; re-running is a no-op; a DB with the columns already present but a stale version doesn't get double-`ALTER`ed; a brand-new install whose `CREATE TABLE` already has every column still ends up at the latest version). Live-verified against the dev database: `PRAGMA user_version` went from unset (0) to 2, `PRAGMA table_info(projects)` confirmed both columns, and login/dashboard kept working after the restart.
- [x] Backup is one-way — done 2026-08-09: new `apps/server/src/restore.ts` (`npm run restore -- <backupDir> [--owner email]`), the direct counterpart to `backup.ts` — bulk-imports a directory of `.dbml` files, each becoming a **new** project (never overwrites an existing one, so restoring the same backup twice makes duplicates rather than risking data loss). Reuses `applyVisualMetadata`/`toProject` from the engine to restore position/zones/sticky notes from backup.ts's sidecar comment when present, writes straight into a fresh `Y.Doc` via `writeProjectToDoc` and `saveSnapshot` — no server process or live Room needed, same standalone-script style `backup.ts` already uses. `--owner <email>` sets the restored project's owner (there's no "reassign owner" route yet, so this is the only way to make one manageable by someone other than a global admin); without it the projects are still viewable by any user (the standard ownerless/no-team default) but only a global admin can manage them, and the script warns about this loudly. 4 new tests for the two pure helpers (filename→name recovery, arg parsing). Live-verified end-to-end against the dev database: backed up a real project, restored it under a new id with `--owner`, confirmed via the running server's own API that the restored project's DBML export and table/field/enum content matched the original exactly, then deleted the test artifact.
- [x] No request/frame size limits tuned for this app — done 2026-07-31: `bodyLimit` 4MB (up from Fastify's 1MB default, for large DBML/SQL imports) and WebSocket `maxPayload` 8MB, both overridable via `ATHANORDB_MAX_BODY_MB` / `ATHANORDB_MAX_WS_FRAME_MB`.
- [x] No startup config validation — done 2026-07-31: `apps/server/src/config.ts` is the only place reading `process.env` now, validating every value and exiting with a `[config] ...` message on anything malformed. ## Phase 19 — Security hardening for professional use

Added 2026-08-09 from the V1 gap analysis ([`v1-roadmap.md`](./v1-roadmap.md) §1). Phase 13 hardened the auth system against the attacks it already faced; this phase is about what a paying team with sensitive schema data expects to exist. Everything below was verified absent in the code today, not assumed.

- [ ] No self-service password reset — **M**. `admin/ResetPasswordModal.tsx` and `PATCH /api/users/:id/password` are admin-only; a user who forgets their password is stuck until an admin is available. `routes/invitations.ts` is the right template (single-use token, expiry, `accepted_at`-style claim inside a transaction). Blocked on the same missing piece as invitation email: with no SMTP, the reset link has to be relayed by an admin, which defeats the point — do this and Phase 13's email item together.
- [x] No session revocation — done 2026-08-09: migration 4 adds `sessions.user_agent`/`sessions.ip`, recorded at login (user-agent truncated to 256 chars — attacker-controlled input shown back in the user's own list). `GET /api/auth/sessions` (own sessions only, current one flagged), `DELETE /api/auth/sessions/:id` (scoped by `user_id`, so an id guessed elsewhere is useless — and clears the cookie when you revoke the session you're using), `POST /api/auth/sessions/revoke-others`. UI in `settings/ActiveSessions.tsx` under _Paramètres → Profil_, with a user-agent → readable-device helper that falls back to the raw string rather than "unknown" (a non-browser client is exactly what's worth noticing). 5 new tests in `session.test.ts` covering cross-user isolation both ways. Live-verified: two sessions listed with device/IP/last-seen, `revoke-others` returned `{"revoked":1}` and left exactly the caller's own.
- [x] Users can never be deleted or disabled — done 2026-08-09, and this turned out to be the largest gap in the list. Migration 3 adds `users.disabled_at`; `resolveSession` refuses a disabled account (so _every_ route including the WebSocket rejects it, without each one knowing about the flag); `PATCH /api/users/:id/disabled` sets it and deletes that account's sessions in one transaction, then calls `revalidateAllRooms()` so a socket authenticated before the change is closed rather than surviving. `DELETE /api/users/:id` removes the account, its sessions, team memberships, pending invitations it sent and its lockout counter, and takes an explicit `transferProjectsTo` — the alternative is leaving the projects ownerless, which is a one-way door since there's no re-assign-owner route. Revision authorship is deliberately **not** rewritten (it's a display name captured at edit time, and erasing who made a change is the opposite of what a trail is for). Two guards: you cannot disable or delete yourself, and neither may remove the last active administrator. UI: disable/enable and delete in `admin/UsersTab.tsx`, with `admin/DeleteUserModal.tsx` putting the project-transfer choice _before_ the decision and requiring the email typed to confirm. Live-verified end-to-end: disabled account's login returned 403 "this account has been disabled", self-disable was refused 400, re-enable worked, delete removed the row and reported `projectsAffected`.
- [ ] No 2FA/MFA — **M** for TOTP, **L** for passkeys. Expected of any tool holding a client's production schema structure.
- [x] `canWrite` is frozen at WS connect — done 2026-08-09: `Room.join` now takes an `AccessResolver` callback instead of a boolean, and `receive()` re-resolves through a 5-second TTL cache (a drag emits dozens of frames a second, each of which would otherwise cost up to four SQLite reads). The TTL is only the backstop: `revalidateRoom(projectId)` is called by the project-grant routes and `revalidateAllRooms()` by team membership/deletion and account disable/delete, so the normal path is immediate. A resolver returning `null` — access lost entirely, not just downgraded — **closes the connection** rather than silently demoting it, and a resolver that throws fails closed. Kept as a callback so `room.ts` stays unaware of how permissions are modelled. 7 tests in `yjs/room.test.ts`.
- [x] No audit log — done 2026-08-09: migration 6 adds `audit_log`; `audit.ts` holds a typed `AuditAction` union, a never-throwing `audit()`/`auditUser()` (the action has already happened by the time it runs — turning an audit failure into a 500 would report a successful operation as failed) and a `listAuditLog()` with filters and a clamped limit. Hooked into project create/delete/archive/restore/import/export/revision-restore, team grant/revoke, team create/delete, membership add/remove, password reset, account disable/enable/delete, session revocation, invitation create/revoke/accept, and locked-login attempts. Deliberately **not** hooked into schema edits: the Yjs revision log already records those with their author, and burying twenty meaningful rows under thousands of keystroke-level ones is how audit logs become unusable. Read-only `GET /api/audit` (admin) — no write or delete route, on purpose. UI: `admin/AuditTab.tsx` with an action filter. 8 tests in `audit.test.ts`, including that a failing write doesn't throw into the caller. Live-verified: nine distinct action types recorded through real requests, with actor, target, detail and IP.
- [x] No per-account project limit — done 2026-08-09: `MAX_PROJECTS_PER_USER = 500` in `routes/projects.ts`, checked against owned projects on create (409 when reached). Trashed projects still count — they're recoverable, so they still occupy the quota. An abuse ceiling, not a plan limit.
- [x] No account lockout or failed-attempt tracking — done 2026-08-09: `auth/lockout.ts` + migration 5's `login_attempts` table. Ten failures against one account locks it for fifteen minutes; the lock is checked _before_ scrypt runs (a locked account shouldn't keep paying ~100ms per attempt — that amplification is what the lock exists to stop), the tripping attempt reports the lock itself rather than granting one more try, an expired lock resets the counter instead of re-locking on the next typo, and stale rows are swept on the same hourly schedule as expired sessions. Failures are only recorded for accounts that **exist**, which both bounds the table by real account count and is a deliberate enumeration tradeoff — documented in the file: a self-hosted team tool where colleagues' addresses aren't secret, versus leaving a legitimate user locked out with no explanation. 7 tests in `auth/lockout.test.ts`.
- [x] `npm audit` is not a CI gate — done 2026-08-09: an `npm audit --audit-level=high` step in `.github/workflows/ci.yml`, `continue-on-error: true`. Both choices are deliberate and commented in the workflow: `high` because the repo carries one known moderate finding (esbuild's dev server, fixable only by a Vite major), and a gate that is red on day one gets ignored; non-blocking so a newly-published advisory surfaces in the run summary without blocking an unrelated PR.
- [x] No documented secret management — done 2026-08-09, by answering the question rather than adding machinery: the README now states plainly that **none of the configuration is a secret** — there is no API key, no signing key and no external-service credential anywhere in it — so plain environment variables are adequate and a secret manager would be ceremony around nothing. It also names the point at which that stops being true: storing a live database connection string (roadmap §7), which needs encryption at rest and brings its own key-management decision.

## Phase 27 — Live database link & deployment

From [`v1-roadmap.md`](./v1-roadmap.md) §7 — the largest and most strategically differentiating gap, and the one where a mistake destroys a client's data rather than annoying them. **Each phase needs its own security review before implementation, not an audit afterwards.**

- [~] Phase A — read-only connection & introspection — **M-L**. A first cut landed 2026-08-15 (not written by the session that then reviewed and hardened it — found already in the working tree, uncommitted, and not yet typechecking): `modules/connections/` (crypto, per-engine drivers, repository, routes) and the web-side `ConnectionManagerModal`/`DeploymentModal`. It arrived _ahead_ of B–D below, not after — introspection, drift diffing (`diffTargetAgainstLive`, reusing `diff.ts` per Phase B's own prediction), migration SQL generation, and apply-with-resolutions all showed up in the same pass. What actually shipped this session, on top of getting it to compile/lint/test clean: this line's own headline risk (SSRF) was **not addressed at all** in the found code — every network driver dialed whatever host/port a caller supplied with zero guarding, and the SQLite driver would open any filesystem path handed to it, including — untested until this pass — AthanorDB's own database file, which would have handed out full read/write SQL access to every password hash, session token and audit row in the instance. Also found: connection credentials were "encrypted" at rest with a key that silently fell back to a hardcoded string baked into public source when `ATHANORDB_SECRET` was unset — encryption in name only. Fixed:
  - `crypto.ts` — no fallback key; refuses to encrypt/decrypt (a clear, client-facing error, not a masked 500) until `ATHANORDB_SECRET` is set.
  - `hostGuard.ts` — blocks the cloud-provider metadata endpoint (169.254.169.254 and its ECS/GCP/Azure/IPv6 variants) for postgres/mysql, resolving the hostname first so a DNS name pointing there doesn't slip through. Deliberately **not** a general private-IP blocklist — a self-hosted deployment's own database is routinely on `localhost` or a LAN address, and blocking that would break the feature's primary use case. DNS-rebinding (resolve-safe, connect-elsewhere) is a known, accepted gap.
  - SQLite driver refuses to open AthanorDB's own configured `ATHANORDB_DB_PATH`. Opening _some other_ sensitive file on the server's filesystem is a real, still-open residual risk this does not close.
  - Every mutating/executing connections route now requires project `administrator`, not `edit` — raised from what the found code had. The web toolbar buttons are hidden from non-admins to match, rather than leaving a 403 as the only signal.
  - `apply-deployment`'s failure path now attempts an explicit `ROLLBACK` for Postgres/SQLite. MySQL's DDL auto-commits per statement regardless of any transaction wrapper — a real engine limitation, not a bug — so a failed MySQL migration can leave a partial result applied with no automatic way back; documented in `migrationGenerator.ts` and `mysql.ts` rather than papered over.

## Open decisions (revisit as needed)

- Auth model: resolved — full email/password auth with sessions, per-project/team permissions, invitations, and an admin console are implemented (`apps/server/src/auth/*`, `apps/server/src/routes/{auth,invitations,teams,users}.ts`, `apps/web/src/{Login,AdminConsole,AcceptInvite,ChangePasswordModal,ProjectTeamsModal}.tsx`) — supersedes the earlier "simple username" plan. No external IdP integration.
- Canvas library: React Flow chosen over building custom SVG/canvas engine, for speed; revisit if performance issues with very large schemas (500+ tables).
- History storage: Yjs update log + periodic SQLite snapshots, avoids storing full doc on every change.
- SQLite as a _SQL import/export dialect_ is not supported by `@dbml/core` (only postgres/mysql/mssql/snowflake/schemarb). SQLite is still used as AthanorDB's own storage engine (unrelated concern). Partly answered by Phase 17: SQLite **export** now ships as the example plugin (generated straight from the `Project`, no parser needed); SQLite **import** would still need a DDL parser.
- Plugin trust model: sandboxed Worker + per-browser install, no server-side plugin store. Revisit if plugins need to be shared across a team — that would mean the server storing third-party code and every user of an instance inheriting an admin's decision to install it.

Opened 2026-08-09 with the V1 gap analysis. Each of these is a decision that has been made implicitly by not deciding; the cost of leaving them implicit is that the product claims one thing and does another.

- ~~**Dark-only or light theme for V1?**~~ **Resolved 2026-08-15: light ships, dark stays the default.** See Phase 22's theme item for what shipped and what's still out of scope (README/landing page still describe the app as dark-only and need updating to match).

- **Does the API come before or after the DB link?** Phase 27's Phase E is blocked on Phase 21's API, but Phases A–D are not. The API unblocks more (webhooks, CI, integrations); the DB link differentiates more. Sequencing them explicitly beats discovering the dependency mid-build.
- ~~**French, English, or real i18n?**~~ **Resolved 2026-08-09: all-French, no i18n library.** Every user-facing string is now French (the admin console, both password flows and the team modals were the stragglers, not just the three files the audit named).
